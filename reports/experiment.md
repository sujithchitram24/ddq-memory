# Structured DDQ Memory: experiment report (exploratory)

All data is synthetic and fictional. This is an independent proof of work. It does not
describe or reproduce any company's system, and results on 3 synthetic documents say
nothing about production performance.

Numbers below come from `reports/results.md`, generated by `scripts/run_eval.py`
(deterministic provider; two consecutive runs produced identical summaries).

## Hypothesis

When DDQ answers are stored as flattened text, table headers and row labels can become
separated from their values. Keeping tables as structured, typed records with source
references makes retrieved evidence more reliable for answering DDQ questions.

## Method

| | |
|---|---|
| Corpus | 3 fictional funds: PDF (fees, track record), DOCX (merged two-row header, conflicting term, qualified minimum), XLSX (5 sheets, %-formatted numbers, year columns, `n/a`, formula without cached value) |
| Questions | 34 hand-written: 30 answerable, 4 where the answer is absent. 14 categories (fee rate + basis, look-alike metrics, period columns, footnotes, conflict, qualification, merged header, missing value, parser limitation, ...) |
| Independent variable | representation: **flat** (text + markdown tables, chunked) vs **structured** (table rows of typed facts + prose chunks) |
| Secondary variable | chunk size: 50 vs 200 words |
| Held fixed | parser output, corpus, questions, k = 5 evidence items, answer algorithm |
| Reader | deterministic extractive reader: chooses the single evidence line with the highest word overlap; abstains below 50% overlap (threshold fixed in advance) |

Metrics: *correct* (all expected values in the answer), *association* (one cited
evidence item contains the values **and** their labels), *citation* (cited evidence
contains the values), *retrieval hit* (any retrieved item contains values + labels),
abstention behaviour, unsupported numbers.

## Results

| Metric | flat/50 | flat/200 | structured/50 | structured/200 |
|---|---|---|---|---|
| Correct answer | 21/30 | 21/30 | 26/30 | 26/30 |
| Value + labels together in cited evidence | 20/30 | 25/30 | 26/30 | 26/30 |
| Cited evidence contains the values | 22/30 | 27/30 | 26/30 | 26/30 |
| Retrieved evidence contains values + labels | 20/30 | 26/30 | 27/30 | 27/30 |
| Correct abstention (answer missing) | 3/4 | 3/4 | 3/4 | 3/4 |
| Abstained although answerable | 0/30 | 0/30 | 0/30 | 0/30 |

Extraction: 3/3 corpus documents processed; failure fixtures behaved as designed
(scanned PDF → `needs_ocr`, corrupt PDF → `CORRUPT_FILE`, blank-header XLSX → processed
with `missing_header` flag; see `tests/test_reliability.py`).

## What the numbers do and don't show

1. **Structured results did not depend on chunk size** (27/30 retrieval hits at both
   sizes). Flat retrieval depended heavily on it: 20/30 at 50 words, 26/30 at 200.
   That is the clearest support for the hypothesis: with small chunks, tables get cut and
   rows lose their headers.
2. **Even at 200 words a table was split.** In the Harbor Lane DOCX, the "Weighted
   average yield" and "Default rate" rows landed in a chunk without the "Fund I / Fund II"
   header row (hl-05, hl-06). The answer text happened to contain the right number, but
   the evidence could not say *which fund* it belonged to.
3. **The 26 vs 21 correct-answer gap overstates the effect.** At 200 words flat
   retrieval found the right evidence 26 times, yet the flat answers were right only
   21 times. The extractive reader picks one *line*; in flat text the header line
   (`| Fee | Rate | Calculated on | Payment |`) often overlaps the question more than the
   data row, so the reader returned the header (hl-01, sr-01, sr-05). An LLM reading the
   whole chunk would probably connect header and row. **Not yet measured.**
4. **Small n.** With 30 answerable questions, a 5-question difference is not a
   statistically established effect. Treat these results as exploratory.

## Failure examples (both strategies)

| Question | What happened | Root cause |
|---|---|---|
| hl-04 fund term | Returned "7 years" only; the prose says "eight years" | **Conflict.** A one-line extractive reader cannot report two sources. Needs a reader that compares evidence |
| sr-06 minimum commitment | Returned USD 10m; missed the USD 7.5m first-close note on another sheet | **Cross-sheet qualification** not linked to the fact |
| nw-14 co-investment fee | Answered with the main management fee instead of abstaining | **Lexical-overlap abstention** is too weak: "management fee" matched |
| sr-08 GP commitment | Empty value | **Parser limitation:** formula with no cached value. Flagged, not invented (correct behaviour, still a failed answer) |
| nw-02 post-investment fee (structured) | Picked the *investment period* row | Footnote text attached to that row inflated its word overlap: **attaching footnotes helps nw-04 and hurts nw-02** |

## Limitations

- One person wrote the corpus, the questions and the hypothesis (risk of designing for success).
- 3 documents, ~500 words each; real DDQs are 50–200 pages.
- The association metric is co-occurrence in one evidence item; a 200-word chunk holding
  a whole small workbook satisfies it trivially.
- The deterministic reader is not an LLM; the generation-level effect is unmeasured.
- Lexical search only; no synonyms or embeddings.
- No OCR; scanned PDFs are rejected with a clear status.

## Architectural implications

- Keep **both** representations: facts for tables, text for prose, footnotes and
  qualifications. Prose answered nw-10 and hl-08; tables answered fee and performance
  questions.
- Store **provenance and processing versions on every fact**; it made every failure
  above debuggable in minutes.
- Parser quality flags should flow into answers ("this value comes from a table flagged
  `missing_header`").

## Next experiments

1. Same evaluation with an LLM reader (`--provider anthropic`), several runs to measure
   variance. Cost per run is small (~140 short calls).
2. A **strong flat baseline**: repeat the header row in every chunk that contains table
   rows. If it matches structured, the cheap fix is enough.
3. A larger corpus (multi-page tables, repeated headers across pages) and 100+ questions
   written by someone who didn't build the system.
4. Hybrid retrieval (FTS + pgvector) and explicit conflict detection across sources.
