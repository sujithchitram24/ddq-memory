# Structured DDQ Memory
Built over four days as a proof of work.

**Does keeping financial tables as structured, typed data make evidence for LLM answers
more reliable than flattened text?** A small FastAPI + PostgreSQL service that ingests
PDF, Word and Excel DDQ (due diligence questionnaire) documents, stores every table both
ways, and measures the difference on a repeatable evaluation set.

> All funds and numbers in `corpus/` are **fictional** and generated by
> `scripts/make_corpus.py`. This is an independent proof of work, not a reproduction of
> any company's system.

Read next: [experiment report](reports/experiment.md) · [generated results](reports/results.md) ·
[database design](docs/DATABASE.md)

## Result (exploratory, 34 questions, offline deterministic reader)

| | flat/50 | flat/200 | structured/50 | structured/200 |
|---|---|---|---|---|
| Correct answer | 21/30 | 21/30 | 26/30 | 26/30 |
| Retrieved evidence holds value + its labels | 20/30 | 26/30 | 27/30 | 27/30 |
| Correct abstention | 3/4 | 3/4 | 3/4 | 3/4 |

Structured retrieval didn't depend on chunk size; flat retrieval did. Part of the
answer-level gap comes from the simple reader. See the report for caveats and failures.

## Architecture

```
client ─► FastAPI ─► validate ─► store file ─► [documents, versions, jobs] (1 transaction) ─► 202
                                                      │
worker ◄── claim job (FOR UPDATE SKIP LOCKED, lease) ─┘
  └─► parse PDF/DOCX/XLSX ─► common format ─► flat chunks + typed facts ─► 1 transaction ─► active run
question ─► retrieve (flat | structured) ─► answer (offline | Claude) ─► validate citations ─► answer + evidence
```
One Postgres = database + job queue + full-text index. No extra services.

## Quickstart (macOS, local Postgres)

Prerequisites: [uv](https://docs.astral.sh/uv/), PostgreSQL 16 running locally.

```bash
psql -d postgres -c "CREATE ROLE ddq LOGIN PASSWORD 'ddq_local_only';" \
  -c "CREATE DATABASE ddq OWNER ddq;" -c "CREATE DATABASE ddq_test OWNER ddq;"
cp .env.example .env
uv sync
uv run python -m scripts.make_corpus     # generate synthetic documents + failure fixtures
uv run alembic upgrade head              # create the schema
uv run pytest                            # 57 tests
uv run python -m scripts.run_eval        # full experiment -> reports/results.md
```

Run the service (two terminals):
```bash
uv run uvicorn app.main:create_app --factory --reload   # http://localhost:8000/docs
uv run python -m app.worker
```
```bash
uv run python -m scripts.create_org "Me"                 # prints an API key once
curl -H "X-API-Key: $KEY" -F file=@corpus/northwind_growth_iii.pdf localhost:8000/documents
```

Or with Docker (needs Docker Desktop running): `docker compose up --build`.

## API

| Method | Path | Purpose |
|---|---|---|
| POST | `/documents` | upload PDF/DOCX/XLSX → 202 (new) or 200 (same bytes already uploaded) |
| GET | `/documents` | list (paginated) |
| GET | `/documents/{id}` | metadata |
| GET | `/documents/{id}/status` | processing status, job attempts, errors, run stats |
| GET | `/documents/{id}/tables` | extracted tables with headers, footnotes, quality flags |
| GET | `/documents/{id}/records` | typed facts with provenance (`?validation_status=unparsed`) |
| POST | `/documents/{id}/retry` | re-queue a `dead` job (409 for permanent failures) |
| POST | `/search` | evidence for a query, `strategy: flat|structured`, `chunk_size: 50|200` |
| POST | `/questions` | answer + cited evidence, or explicit abstention |
| POST | `/evaluations` | run the evaluation set |
| GET | `/evaluations/{id}` | summary (`?include_results=true` for per-question scores) |
| GET | `/health/live`, `/health/ready` | liveness (no DB) / readiness (DB) |

All requests except health need `X-API-Key`. Errors: `{"error": {"code", "message", "request_id"}}`.

## Status and limitations

Verified locally: tests, evaluation, live API. **Not verified:** the Docker image build
and Kubernetes manifests (YAML parses; no cluster or Docker daemon was available).
No OCR (scanned PDFs → `needs_ocr`). Auth is a local API-key mock. Files on local disk
(S3 in production). Details in [reports/experiment.md](reports/experiment.md).

## Security: what is implemented vs what production needs

| Implemented here (local demo grade) | Production would add |
|---|---|
| API key → organisation; only the key's hash is stored | OIDC/JWT identities, key rotation, rate limits |
| Every query filtered by `org_id`; cross-tenant access returns 404 (tested) | Postgres Row-Level Security as a second layer |
| Extension + magic-byte checks, size cap, zip-bomb check | Malware scanning; parsing in a sandboxed container without network |
| Storage keys generated by the server, never from filenames | S3 with per-tenant prefixes, IAM policies, encryption at rest |
| Parameterised SQL only | Least-privilege database roles |
| Secrets from environment; `.env` git-ignored; passwords redacted in logs | AWS Secrets Manager + IAM Roles for Service Accounts |
| Documents treated as untrusted input; answer citations validated | Tool-level permissions for agents, human review for high-stakes answers |
